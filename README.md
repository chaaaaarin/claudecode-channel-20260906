## まず3行で（TL;DR）

- AIの答えが「惜しいけど違う」ものになるのは、AIの実力不足ではなく、**「何をしてほしいか」をこちらが言葉にしていないから**であることが多い。指示が下手なのではなく、指示をしていない。

## 1. 「AIがアホ」なとき、実際に起きていること

きっかけは、AI論文データベース **AIDB（エーアイディービー／@ai_database）** の2026年8月28日の投稿。

> AIが強力になればなるほど、正確な人間の仕様書作りがより重要になるパラドックス。指示に従って完成品を作る能力がどんどん増している。だから仕様書の重要性がますます上がっていて、人間が「なにをしたいか（作りたいか）」を突き詰める必要がある。

この投稿と関連記事は解説メディア（二次情報）なので、ここから先の事実は公式の発表・調査で裏づける。

いま、SNSや個人ブログには「AIに全部作らせたけど使えなかった」という失望も広がっている（「2ヶ月で破綻したWebサービス」「ミニアプリを量産してもユーザー0・収益0」など）。これらも個人の発信なので、根拠ではなく“空気”として置いておく。

**これは他人事ではない。** その「使えないAI」に、あなたが毎日渡している CLAUDE.md（クロードエムディー）やスキルの説明文（SKILL.md）。公開されている SKILL.md を **138,133件調べた研究では、91.8% に1つ以上の欠陥**があり、その大半は難しい技術的問題ではなく「書き方・まとめ方」の問題だった（[arXiv:2608.08453](https://arxiv.org/abs/2608.08453)・確度 ✅）。

では、その失望のとき、実際に何が起きているのか。開発者およそ4.9万人に聞いた **Stack Overflow（スタックオーバーフロー）Developer Survey 2025** の数字がわかりやすい（[survey.stackoverflow.co/2025/ai](https://survey.stackoverflow.co/2025/ai)・確度 ✅）。

| 指標 | 数字 | 意味 |
|---|---|---|
| 最大の不満 | **66%** | AIの答えが「惜しいけど違う（almost right, but not quite）」 |
| 2番目の不満 | **45%** | AI生成コードのデバッグに時間がかかる |
| AI出力の正確性を「強く信頼」 | **3%** | 残りは半信半疑〜不信 |

「惜しいけど違う」が生まれる仕組みは、GitHub（ギットハブ）公式ブログが端的に書いている（[github.blog](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)・確度 ✅）。

> "A vague prompt like 'add photo sharing to my app' forces the model to guess at potentially thousands of unstated requirements."
> （「アプリに写真共有をつけて」のようなふわっとした一言は、言葉にしていない何千もの要件をAIに“推測”させることになる）

たとえば「ログイン機能を付けといて」だけ渡すと、AIは「SNSログインも？」「パスワード要件は？」「2要素認証は？」「セッションはどこで持つ？」「エラー文言は？」を全部“推測”で埋める。1つずれるごとに、完成物は少しずつ意図から離れていく。だからAIDBの記事も「このずれは “AIの能力不足” ではなく “人間が作成した仕様の問題” かもしれない」と書いている。**ここがこの動画の出発点。**

## 2. なぜ賢くなったAIで、逆に人間の仕事が増えるのか（パラドックス）

直感に反するが、**AIが「作る」を上手にやるほど、「なにを作るか」の比重が上がる**。

OpenAI（オープンエーアイ）のショーン・グローブは、登壇「The New Code」（2025年6月）でこう言っている（[youtube.com/watch?v=8rABwKRsec4](https://www.youtube.com/watch?v=8rABwKRsec4)・確度 🔶＝割合は書き起こしベース）。

- コードそのものが生む価値は全体の **10〜20%**。残り **80〜90%** は「構造化された伝達」＝仕様。
- "In the near future, the person who communicates most effectively is the most valuable programmer."（これからは、いちばん的確に伝えられる人が、いちばん価値のあるプログラマーになる）
- コードは仕様からの“劣化コピー”。コンパイル済みのファイルを戻しても、きれいな変数名やコメントは戻らないのと同じ。

AIが左（コードを書く作業）を高速化した。だから差がつくのは右——**曖昧さなく伝えられるか**。これがパラドックスの正体。

<a id="s3"></a>
## 3. 「言っていない」と「言っている」の違い

難しい文章術ではない。頭の中の「当たり前」を、**4つの枠**に出すだけ。

| 枠 | 書くこと |
|---|---|
| 目的 | 最終的に何ができれば成功か |
| 成功条件 | どうなったら「できた」と言えるか |
| 制約 | 使う技術・分量・形式・締切（新規ライブラリの可否など） |
| やらないこと | 触ってほしくない範囲 |

4つ全部を最初から完璧に書く必要はない。**1つ足すごとに、AIの“推測”が1つ減る。**

### 実例：同じお願いを書き直す

**Before**：「ログイン機能、いい感じに付けといて」（対象ユーザーも、認証方式も、やらない範囲も伝えていない）

**After**：
- 目的：既存ユーザーがメール＋パスワードでサインインできる
- 成功条件：誤入力でエラー表示・成功でダッシュボードへ・既存のセッション処理に乗る
- 制約：新規ライブラリ追加なし・既存のフォーム部品を使う
- やらないこと：SNSログインとパスワード再発行は今回対象外

同じAI・同じモデルでも、返ってくるものが変わり、やり直しが減る。

### 4つの枠を、Claude Code の機能で仕組みにする

毎回手で書かなくても、枠ごとに“置き場所”がある。

| 枠 | Claude Code だとこうする |
|---|---|
| 目的・成功条件 | **Plan Mode** で計画を先に出させて、着手前に見る |
| 制約・やらないこと | **CLAUDE.md** に常設。毎回書かずに効かせる |
| 繰り返す注文 | **スラッシュコマンド／スキル**に固める |
| 大きい仕事 | **サブエージェント**に“仕様つきで”渡す |

枠は同じ。Claude Code は、それを「毎回書く」から「仕組みで持つ」に変えられる。

### そのまま使える「頼む前の1文」

```text
このタスクの「完成した状態」を1文で言うと〔　　　〕。
できたと判断する基準は〔　　　〕。
〔　　　〕はやらないで。
まず叩き台を出して。確定はこちらでする。
```

<a id="s4"></a>
## 4. Claude Code でやりがちな「渡し方」の失敗

指示の型が分かっても、つい戻ってしまうクセ。1つでも当てはまったら、そこが伸びしろ。

| やりがち | 直し方 |
|---|---|
| セッションを片づけずに次を頼む（古いやり取りが残ったまま） | 区切りで `/clear` か新セッション |
| 複数ファイルにまたがる依頼を1メッセージで丸投げ | 手順と触るファイルを先に出させて合意 |
| CLAUDE.md が「AIっぽい文体やめて」だけ（OK例・NG例なし） | 具体例と、迷ったときの優先順位を3行 |
| 関連ファイルを指さず「そのへん直しといて」 | 対象と、似た既存実装のファイルを先に指す |
| Plan Mode を使わず即実装させる（方針ごとズレる） | 計画を見て合意してから着手 |
| サブエージェントに1行で丸投げ | 完成条件と「迷ったら止まって聞く」を渡す |

どれも「AIが弱い」のではなく、渡し方の空欄。埋めれば返りが変わる。

<a id="s5"></a>
## 5. 大げさな「仕様書」を、個人サイズにする

開発の世界では「まず仕様、次にコード」に本気で舵を切る動きが進んでいる。代表例が GitHub（ギットハブ）の **Spec Kit（スペックキット）**（[github.com/github/spec-kit](https://github.com/github/spec-kit)・確度 ✅）。

- GitHubスター数は **約13.4万**（2026年9月時点）＝一部の流行りではない
- 対応するAIコーディング支援は **30種以上**（Claude Code・Copilot・Cursor・Codex CLI などを含む。特定ツール専用ではない）
- バージョンは **1.0** に到達（実験ではなく実用フェーズ）

その型（左）を、ひとり用に読み替えると（下）こうなる。

| 開発の型 | 読み替え | 個人ならこうする |
|---|---|---|
| Constitution | 憲法 | 毎回守ってほしいルール（口調・NG） |
| Specify | 要件 | 完成の姿と成功条件を1〜3行 |
| Plan | 段取り | 使う道具・進め方を先に決める |
| Tasks | 分割 | 大きい仕事は小さく割る |
| Implement | 実装 | AIに作らせる |
| Converge | 照合 | 要件どおりか見比べて直す |

個人なら **「憲法・要件・やらないこと」の3つ**を最初に書くだけでも、推測が大きく減る。

<a id="s6"></a>
## 6. コードの外でも、同じことが起きる

「指示の質＝出力の質」は、AIにコードを書かせる場面に限らない。Claude Code（クロードコード）を使ううえで人間が書く“指示ファイル”は、どれも同じ原理で効く。

- **CLAUDE.md（クロードエムディー）**：「AIっぽい文体をやめて」だけでは毎回ブレる。OK例・NG例・迷ったときの優先順位を短く具体的に
- **スキルの説明文（SKILL.md〈スキルエムディー〉）**：説明が曖昧だと、必要なときに呼び出されない
- **サブエージェントへの依頼文**：頼み方が曖昧だと、空回りや脱線が起きる
- **MCP（エムシーピー）ツールの説明文**：曖昧だと、AIが使い方を誤る

前述の SKILL.md 138,133件の調査（[arXiv:2608.08453](https://arxiv.org/abs/2608.08453)・確度 ✅）では、欠陥の大半が次の3つに分かれた。

| 欠陥のタイプ | 起きること |
|---|---|
| 説明文が弱い（1文目で「何をする・いつ使う」が言えていない） | 必要なときに呼ばれない |
| 本文が肥大（関係ない前置き・重複で埋まっている） | AIが要点を拾えない |
| 整理されていない（参照ファイル・例の置き場所がバラバラ） | 再利用できない |

直し方は同じ「4つの枠」。CLAUDE.md も SKILL.md も、OK例・NG例・迷ったときの優先順位を短く具体的に書く。アンドレイ・カルパシー（Andrej Karpathy）は「英語は自然言語のプログラミング言語」と言う（Software 3.0・[youtube.com/watch?v=LCEmiRjPEtQ](https://www.youtube.com/watch?v=LCEmiRjPEtQ)・確度 ✅）。人間が書くファイルは、もうどれも“プログラム”だという話。

<a id="s7"></a>
## 7. じゃあAIは悪くないのか（限界とコスト）

「全部人間のせい」ではない。指示を完璧にしても、AI側の弱点は残る。

- **凸凹（でこぼこ）知能**（jagged intelligence／カルパシー）：すごいことができる一方で、突然ばかみたいなミスをする。桁の多い暗算や、曖昧な指示の解釈で急に落ちる。仕様を固めても“谷”は残る。
- だからAIは **検証を速くできる仕事** に向く。丸ごと任せて放置はしない（最初の出力は“叩き台”扱い）。
- **仕様を書くコスト**：仕様を書く時間が作業時間より長くなったら本末転倒。小さい依頼は身軽に投げてよい。

### 「仕様を書く」のメリットとコスト

| 観点 | 仕様を書くと | 書かないと |
|---|---|---|
| やり直し | 減る（一発で近づく） | 増える（何度も投げ直し） |
| 最初の手間 | 数分かかる | すぐ投げられる |
| ブレ | 小さい・再現しやすい | 毎回変わる |
| 向く仕事 | 完成の姿を言葉にできるもの | 輪郭がないフワッとした探索 |

（参考：カルパシー登壇「Software Is Changing (Again)」・確度 🔶）

<a id="s8"></a>
## 8. 「指示する」と「考えさせる」の線引き

| こういう仕事は | やること |
|---|---|
| 完成の姿を言葉にできる（定型コード・リファクタ・調査の型） | 仕様を書いて渡す。推測させない |
| 正解の輪郭がまだ無い（アイデア出し・方向の相談） | あえて広く投げて、選択肢を出させる |
| どちらか迷う | まず広く投げ、返ってきた案を見て仕様に落とす |

## 今日からやること（始めるならこの順番）

1. **頼む前に「完成した状態」を1文で書く。** これだけで推測の半分が消える。
2. **「制約」と「やらないこと」を1行ずつ足す。** 使う技術・分量・締切・触ってほしくない範囲。
3. **最初の出力は“叩き台”として受け取る。** 全体をダメ出しせず、気になる差分だけ指示して直す。
4. うまくいった頼み方は、**CLAUDE.md に短くメモして再利用**する。繰り返すものはスラッシュコマンド／スキルへ。

3つとも合計30秒で書ける。それだけで「惜しいけど違う」がかなり減る。

<a id="matome"></a>
## まとめ

- AIの「惜しいけど違う」は、指示が下手だからではなく「何をしてほしいか」を言葉にしていないのが原因。AIの実力不足と決めつける前に、そこを見直す。
- AIが賢くなるほど、人間の仕様の粗さがそのまま結果に出る（パラドックス）。
- 「完成の姿・成功条件・やらないこと」を先に書くだけで変わる。コードでも、CLAUDE.md でも、スキルの説明文でも同じ。Claude Code なら Plan Mode・CLAUDE.md・スラッシュコマンド・サブエージェントで仕組みにできる。
- ただしAIは凸凹知能。仕様を固めても“谷”は残るので、検証を速くできる仕事に使い、叩き台として受け取る。

<a id="kit"></a>
## プレゼント（キットの中身と受け取り方）

「頼み方」を今日から変えるための道具を用意しました。

1. **「"惜しい"を"一発OK"に変える 実装依頼リライターアプリ」**
   曖昧な実装依頼を貼ると、目的／受け入れ条件／制約／対象外／確認方法の5枠に組み替えて、Claude Code にそのまま貼れる形で表示するミニアプリ。「いい感じに直して」で毎回やり直していた人が、1回で欲しい変更が返るようになる。
2. **「CLAUDE.md／SKILL.md 健診シート」**
   自分の CLAUDE.md・SKILL.md を、arXiv 調査でいちばん多かった欠陥3タイプ（説明文が弱い／本文が肥大／整理不足）で1項目ずつ点検。見つかった箇所ごとに、そのまま貼れる直し方の指示例つき。「作ったのに使われない」「毎回ブレる」を、その場で潰せる。
3. **「Claude Codeに頼む前の30秒テンプレ 厳選10」**
   実装／リファクタ／バグ修正／調査／レビュー依頼／CLAUDE.md追記／SKILL.md説明文／サブエージェント依頼など場面別に、埋めれば“仕様”になる短文フォーム10種。考える前に埋めるだけで、30秒で“推測させない”依頼文になる。

**受け取り方**：[プレゼント図書館（ClaudeCodeチャンネル）](https://chaaaaarin.github.io/gift-library/cc/) から。動画の概要欄の公式LINEでも案内しています。
